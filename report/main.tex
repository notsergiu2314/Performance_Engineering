\section{Introduction}
% =============================================================================
CloverLeaf~\cite{mallinson2013} solves the compressible Euler equations on a 2D structured grid with an
explicit Lagrangian--Eulerian scheme; it is a stencil code and a standard case for memory-bound performance
engineering~\cite{laukemann2023}. We work on the reference implementation (\texttt{CloverLeaf\_ref},
commit \texttt{b5e598d}, MPI+OpenMP) and optimise its \emph{C kernels} (\texttt{use\_c\_kernels}) on one
node of the HAICGU cluster. Section~\ref{sec:base} establishes where the baseline stands against the
hardware, Section~\ref{sec:impr} derives the kernel changes that can still pay off and shows them in code,
and Section~\ref{sec:res} compares the optimised kernels with the baseline at every layout.

% =============================================================================
\section{Baseline Analysis}
\label{sec:base}
% =============================================================================
\subsection{Application and system}
One time step runs, in order, the equation of state (\kernel{ideal\_gas}), artificial viscosity, the stable
time step (\kernel{calc\_dt}), a predictor and a corrector PdV step, the node acceleration, the volume
fluxes, the advection of cell quantities (\kernel{advec\_cell}) and of momentum (\kernel{advec\_mom}) in two
directional sweeps, and the reset of the time levels. Every kernel is a loop nest over the grid with a
$\pm1$ stencil; the two advection kernels contain an upwind/limiter loop with data-dependent indices.
All fields are double-precision arrays of $(n_x+5)\times(n_y+5)$ elements.
The benchmark problem is \textbf{bm3840}: $3840^2$ cells, 87 time steps, about 25 arrays of 118\,MB
($\approx$3\,GB working set, far beyond the 2$\times$64\,MB L3), with CloverLeaf's built-in kinetic-energy
check (\texttt{PASSED} in every run reported here).

\begin{sloppypar}
The node has 2$\times$ Kunpeng~920 (ARMv8, 2.6\,GHz, 64 cores each, 4 NUMA domains of 32 cores) and
16 channels of DDR4-2666 (128\,GB, 341\GBs{} theoretical), under a RHEL-8-compatible Linux with 64\,KB
pages. Software: GCC/GFortran 14.1.0, OpenMPI 5.0.3, PAPI 7.1.0 and Linux \texttt{perf}; the kernels are
compiled with the project's \texttt{GNU} settings, \texttt{-O3 -march=native -funroll-loops -fopenmp}.
Nodes are used exclusively. A configuration ``$r\times t$'' is $r$ MPI ranks with $t$ OpenMP threads each. Every rank is
bound to $t$ consecutive cores (\texttt{--map-by slot:PE=}$t$) and OpenMP pins one thread per core
(\texttt{OMP\_PLACES=cores}, \texttt{OMP\_PROC\_BIND=close}). The Fortran kernels are run at the same
configurations for reference only.
\end{sloppypar}

\subsection{Methodology}
\label{sec:method}
\textbf{Tools.} Three independent sources: (1) CloverLeaf's internal profiler (wall clock per algorithmic
phase); (2) PAPI per kernel, through a small instrumentation layer (\texttt{papi\_prof}) that wraps the
\texttt{omp parallel} region of each C kernel, keeps one event set per thread and writes the counts per
thread at exit (compiles to nothing without \texttt{-DUSE\_PAPI}); cycles/instructions, instruction mix and
stall sets are measured in separate runs; (3) Linux \texttt{perf}: sampling profiles, whole-run counters,
and the HiSilicon DDR-controller PMU (\texttt{hisi\_sccl*\_ddrc*/flux\_rd,wr}), read system-wide
around every run, which counts the bytes that cross the memory interface per controller.

\textbf{Protocol.} Five repetitions per configuration, median and min--max reported; the timed region
is the complete run of 87 steps including start-up; every repetition runs under the DDR-controller
counters, so wall clock and hardware bytes belong to the same run. All bandwidths are
\emph{hardware bytes} (DDR-controller counts $\times$ 32\,B) over wall clock, for STREAM and for the
application alike. The harness (\texttt{perf/baseline}) is driven by matrix files and environment
variables and runs through \texttt{mpirun} only.

\textbf{Checks of the tools.} The PAPI build costs nothing measurable (11.30\,s against 11.34\,s at
64$\times$2; 521--523\,s against 528\,s on one core) and its per-kernel times add up to the wall clock
within 1\%; \texttt{MEM\_ACCESS} equals \texttt{PAPI\_L1\_DCA} in every kernel; the cycle counter gives
2.59\,GHz; the DDR counters were calibrated on STREAM (Section~\ref{sec:ceil}). The placement of every
multi-rank run is checked by the counters: the busiest controller group carries $1.00\times$ the mean.

\textbf{Correctness gate.} CloverLeaf's own check on the long deck \texttt{clover\_bm.in} ($960^2$ cells,
2955 steps, test problem 3) reports a deviation of 0.57\% (C) and 1.79\% (Fortran) from the reference
compiled into the code even for the \emph{unmodified} kernels, identical to all digits at every layout and
repetition (Table~\ref{tab:correctness}): the reference was produced on another machine. Every modified
kernel therefore has to reproduce this baseline deviation to $10^{-6}$\% (\texttt{perf/baseline/qa\_check.py})
and print \texttt{PASSED} on bm3840.

\subsection{Where the time goes}
\label{sec:time}
Table~\ref{tab:kernels} gives the time share and the counters of every kernel. The two advection kernels
take 48\% of the time on one core and 63\% on 128; \kernel{advec\_mom} scales worst of the large kernels
(14$\times$ against 22--59$\times$). On one core the IPC is 0.35--1.07 and 60--87\% of the cycles are
back-end stalls; at 64$\times$2 the IPC is 0.10--0.50 per kernel and the stall share 81--96\%: the cores
wait for memory. Three kernel groups appear in the instruction mix: \kernel{pdv}, \kernel{accelerate} and
\kernel{flux\_calc} are vectorised (41--62\% NEON); \kernel{calc\_dt}, \kernel{ideal\_gas} and
\kernel{viscosity} run entirely scalar (they contain \texttt{sqrt}, which GCC keeps scalar without
\texttt{-fno-math-errno}) but are only 12\% of the node-level run; \kernel{advec\_mom} and
\kernel{advec\_cell} are 12--16\% vector instructions because their upwind loops have data-dependent
indices. The \texttt{perf} profile of a 128-thread run adds that 12.5\% of all cycles are spent in the
OpenMP barrier (\texttt{gomp\_team\_barrier\_wait\_end}): every kernel is a sequence of worksharing loops
with an implicit barrier each.

\subsection{Ceilings and byte model}
\label{sec:ceil}
\textbf{Memory.} STREAM triad ($10^8$ doubles, 20 iterations, 10 runs per configuration) sustains
15\GBs{} on one core, 67\GBs{} per NUMA domain (32 threads) and \textbf{266.5\GBs{}} for the node, in every
one of 10 pinned repetitions. Under the DDR-controller counters the controllers move $1.04\times$ the
bytes STREAM counts itself (24\,B per triad element) and $0.74\times$ the write-allocate model, in all 20
STREAM runs and in our own triad kernel: a streaming store does \emph{not} read the line first on this CPU,
one count is 32\,B, and the hardware ceiling is the counted triad, 78\% of the bus. (The DIMM clock is
not readable without root; 266.5\GBs{} over 16 channels needs at least 2082\,MT/s, so DDR4-2666 is
consistent.)

\textbf{Compute.} Independent FMA chains on 2-lane NEON registers reach 4.0\,flop/cycle per core and
\textbf{1330\GFs{}} per node; scalar FMA reaches the same, so vectorisation saves instructions, not flops.
Vector division runs at 0.19\GFs{} per core. The ridge point of the node is $1330/266.5 = 5$\,flop/B
(0.7\,flop/B for one core).

\textbf{Byte model.} For every loop nest of the C kernels we counted the arrays read and written and the
flops per cell; each array is streamed from DRAM once per loop nest, and a store is charged a
read-for-ownership (write-allocate) in addition to the write. Table~\ref{tab:model} gives 451\,flop and
2186\,B per cell and step (1688\,B without the read-for-ownership), an intensity of 0.21\,flop/B.

\textbf{Validation.} The model predicts 2.80\,TB for bm3840; the counters measure 2.83\,TB at 64$\times$2
in all five repetitions (1\% above), 2.79--2.99\,TB at the other layouts. The read/write split decides
which version of the model applies: the counters see 2.05\,TB of reads and 0.77\,TB of writes against
1.53\,TB of demand reads and 0.64\,TB of writes in the model, i.e.\ the reads are $1.34\times$ the demand
reads. Unlike STREAM, the C kernels' stores \emph{do} cause a read of the line first, for about 70\% of the
written volume; the write-allocate model is the right one for the code as it stands. The Fortran build
writes the same amount (0.60\,TB) but reads only $1.15\times$ the demand reads (1.76\,TB, 2.36\,TB in
total): its loops avoid most of that traffic, and this 0.47\,TB is the entire C/Fortran gap
(Section~\ref{sec:perf}).

\section{Kernel Improvements}
\label{sec:impr}
% =============================================================================
\subsection{What the analysis allows}
The baseline sustains 94\% of the memory ceiling, so instruction-side work (vectorising the upwind loops,
\texttt{-fno-math-errno} for the \texttt{sqrt} kernels, fewer barriers) cannot pay off until the bytes shrink;
those items are kept as time-only changes (Section~\ref{sec:timeonly}). The byte count has two components
we can change: the bytes the algorithm asks for (temporaries, dead stores, copies, repeated helper loops)
and the read-for-ownership that the C stores pay and a streaming store would not. Every byte change below
is expressed as an edit of the loop table of the byte model (\texttt{perf/analysis/plan\_bytes.py}), so the
prediction and the later measurement use the same convention, and every change has to pass the
correctness gate of Section~\ref{sec:method}.

\subsubsection{Selection}
The original plan was to take the three kernels with the largest theoretical gain in
the byte model and leave the rest. These are: \kernel{advec\_mom}, whose helper loops are recomputed for every
velocity component. \kernel{reset\_field} and \kernel{revert}, which solely copy data, and
\kernel{advec\_cell}, which round-trips four temporaries through memory. While reading these kernels,
further opportunities presented themselves and were implemented as well: two dead stores
(\texttt{post\_vol}, \texttt{pre\_vol}), the fused reduction of \kernel{calc\_dt}, two compiler flags that
unblock vectorisation, \texttt{nowait} between loops that are provably independent, and a branch-free
formulation of the \kernel{advec\_mom} upwind loop. Changes (1)--(6) below reduce bytes, (T1)--(T4)
reduce time only; Section~\ref{sec:status} gives the state of each.

\subsection{Flop and byte counts per cell}
\label{sec:count}
The counts of Table~\ref{tab:model} were made by reading every loop nest of
\texttt{kernels/*\_kernel\_c.c} and listing: the 2D arrays it reads, the 2D arrays it
writes and the floating-point operations per cell. The bandwidth of bytes per cell of a loop nest is

\[ 
  8\,\mathrm{B}\times(\text{arrays read} + \text{arrays written} + \text{WA}\times\text{arrays written but
not read})
\] 

Every array is streamed from DRAM once per loop nest, since it easily large enough not to fit in cache.
Stencil neighbours $j\pm1$, $k\pm1$ hit in cache (a few rows of 3840 doubles fit in the
512\,KB L2), and the read-for-ownership (WA) is charged once for every array a loop stores without
loading. 1D arrays (\texttt{celldx}, \texttt{vertexdx}, \ldots) and halo cells are ignored. Flops: $+$,
$-$, $\times$, $/$ and \texttt{sqrt} count one; comparisons, \texttt{fabs}, \texttt{MIN}, \texttt{MAX} and
\texttt{SIGN} count zero; loop-invariant constants are hoisted. Kernels whose loops differ between the two
sweeps are averaged over the sweeps. Per kernel and call:
\begin{itemize}\setlength\itemsep{0pt}
  \item \kernel{ideal\_gas}: reads density and energy, writes pressure and soundspeed: four streams, two
        of them write-allocated. Nine flops: $1/\rho$, $0.4\rho$, the product with $e$, $\rho p$, the
        sound-speed expression $v^2(p\,p_e - p_v)$ and one \texttt{sqrt}.
  \item \kernel{viscosity}: four reads (both velocities, pressure, density), one write; 40 flops on the
        common branch, 13 more in compressed cells.
  \item \kernel{calc\_dt}: the first loop reads eight arrays and stores \texttt{dt\_min}, the second loop
        reads \texttt{dt\_min} back; 31 flops for the four limits.
  \item \kernel{pdv}: the predictor reads nine arrays, the corrector eleven (it adds the level-1
        velocities), three writes each; 33 flops.
  \item \kernel{accelerate}: eight reads, two writes; 37 flops. \kernel{flux\_calc}: two loops of three
        reads and one write; five flops each.
  \item \kernel{revert} and \kernel{reset\_field}: one read, one write and one write-allocate per field,
        for two and four fields; no flops.
  \item \kernel{advec\_cell} (two calls per step): the volume loop reads two or three arrays and writes
        \texttt{pre\_vol} and \texttt{post\_vol}; the flux loop reads four and writes two; the update loop
        reads six and writes six, four of which are temporaries nothing else reads. 45 flops.
  \item \kernel{advec\_mom} (four calls per step): six loops, from the volume loop (two or three reads,
        two writes) to the velocity update (four reads, one write); the upwind loop alone has 18 of the
        39 flops.
  \item \kernel{field\_summary}: six reads into reductions, every tenth step; about 22 flops.
\end{itemize}
Multiplied by the calls per step these give the 451\,flop and 2186\,B per cell and step of
Section~\ref{sec:ceil}, which the DDR counters confirmed to 1\%.

\subsection{Byte reductions}
\label{sec:bytes}
Each change is shown on the baseline code; the comments say what is inefficient and what the change does,
the new code follows in Section~\ref{sec:status}. In the C snippets \texttt{i} abbreviates the node-sized
index \texttt{FTNREF2D(j,k,x\_max+5,...)} of cell $(j,k)$, \texttt{iy} the cell-sized one, and
\texttt{i+1} the neighbour $j+1$; \texttt{[(j,k-1)]} writes a stencil neighbour out in full.

\textbf{(1) \kernel{advec\_mom}: direction-only helper loops once per sweep.}
The kernel is called four times per step (two sweeps $\times$ \texttt{xvel}, \texttt{yvel}). Its first four
loops depend only on the sweep direction, not on the velocity component, and are recomputed for
\texttt{yvel} with identical results:
\begin{code}[language={[90]Fortran}]
! advec_mom_driver.f90 (baseline): one kernel call per velocity component
CALL advec_mom_kernel_c(..., xvel1, mass_flux_x, vol_flux_x, mass_flux_y, vol_flux_y, &
                        volume, density1, work_array1..6, celldx, celldy,             &
                        which_vel=1, sweep_number, direction)
CALL advec_mom_kernel_c(..., yvel1, ... same arguments ...,                          &
                        which_vel=2, sweep_number, direction)
! Inside the kernel, loops 1-4 (post_vol, node_flux, node_mass_post, node_mass_pre)
! use only direction and sweep_number: the yvel call rebuilds the four arrays over
! the haloed grid with exactly the values the xvel call produced, i.e. it streams
! mass_flux, vol_flux, volume, density1 and the four work arrays a second time.
! Only loop 5 (mom_flux from the limited upwind velocity) and loop 6 (the vel1
! update) read vel1. Change: split the kernel in a preparation part called once
! per sweep and a velocity part called once per component.
\end{code}

\textbf{(2) \kernel{advec\_cell}: temporaries in registers.}
The update loop of each sweep writes four work arrays and reads them back in the same iteration; nothing
else reads them:
\begin{code}
/* advec_cell_kernel_c.c (baseline), update loop of the x sweep */
pre_mass[i]  = density1[i]*pre_vol[i];                          /* stored here ...        */
post_mass[i] = pre_mass[i] + mass_flux_x[i] - mass_flux_x[i+1]; /* ... and reloaded here  */
post_ener[i] = (energy1[i]*pre_mass[i] + ener_flux[i] - ener_flux[i+1])
               / post_mass[i];
advec_vol[i] = pre_vol[i] + vol_flux_x[i] - vol_flux_x[i+1];
density1[i]  = post_mass[i] / advec_vol[i];
energy1[i]   = post_ener[i];
/* pre_mass, post_mass, post_ener and advec_vol are never read outside this
 * iteration: each costs a full-mesh store plus its read-for-ownership, four
 * arrays of DRAM traffic for values that fit in four registers. Change: make
 * them scalars; the arithmetic and its order stay the same. */
\end{code}

\textbf{(3) Dead stores.}
\texttt{post\_vol} in the first sweep of \kernel{advec\_cell} and \texttt{pre\_vol} in \kernel{advec\_mom}
are written over the whole haloed grid and never read:
\begin{code}
/* advec_cell_kernel_c.c (baseline), sweep 1 (x direction) */
pre_vol[i]  = volume[i] + (vol_flux_x[i+1]-vol_flux_x[i])
                        + (vol_flux_y[iy+1]-vol_flux_y[iy]);
post_vol[i] = pre_vol[i] - (vol_flux_x[i+1]-vol_flux_x[i]);   /* no loop of sweep 1 reads
                                                                 post_vol: dead store */
/* advec_mom_kernel_c.c (baseline), every sweep */
post_vol[i] = volume[i] + vol_flux_y[iy+1] - vol_flux_y[iy];
pre_vol[i]  = post_vol[i] + vol_flux_x[i+1] - vol_flux_x[i];  /* no kernel reads pre_vol; the
                                                                 original source keeps it "for
                                                                 fidelity with the Fortran
                                                                 method" */
/* Each dead store is a full-mesh write plus a read-for-ownership over the haloed
 * grid, once per call. Change: delete both lines (and the pre_vol argument). */
\end{code}

\textbf{(4) Reset and Revert without copies.}
\kernel{reset\_field} copies the four end-of-step fields (\texttt{density1}, \texttt{energy1},
\texttt{xvel1}, \texttt{yvel1}) into their level-0 partners, 118\,MB each; \kernel{revert} copies
\texttt{density0}/\texttt{energy0} back into the level-1 arrays before the PdV corrector because the
predictor wrote into them:
\begin{code}
/* reset_field_kernel_c.c (baseline): one of four identical copy loops */
#pragma omp for private(j)
for (k=y_min;k<=y_max;k++)
#pragma omp simd
  for (j=x_min;j<=x_max;j++)
    density0[i] = density1[i];  /* 118 MB read, 118 MB written, 118 MB read-for-ownership;
                                   the same for energy, xvel and yvel. No kernel needs a
                                   field at a particular address: the fields are
                                   allocatable components of the tile. Change: exchange
                                   the allocations instead of the data. */
\end{code}
\begin{code}[language={[90]Fortran}]
! PdV.f90 (baseline), end of the predictor pass
IF ( predict ) THEN
  CALL revert()   ! density1 = density0, energy1 = energy0 over the whole tile, because
                  ! the predictor wrote density1/energy1. The C corrector recomputes both
                  ! from the level-0 fields over the same range and nothing in between
                  ! reads the level-1 values. Change: skip the call on the C path.
ENDIF
\end{code}

\textbf{(5) \kernel{calc\_dt}: fused reduction.}
The kernel stores the local time step of every cell to \texttt{dt\_min} and reduces the array in a second
loop:
\begin{code}
/* calc_dt_kernel_c.c (baseline) */
#pragma omp for private(...)
for (k...) for (j...) {
    ... the four limits dtct, dtut, dtvt, dtdivt of cell (j,k) ...
    dt_min[i] = MIN(dtct, MIN(dtut, MIN(dtvt, dtdivt)));  /* full-mesh store plus its
                                                              read-for-ownership */
}
#pragma omp for reduction(min:dt_min_val)
for (k...) for (j...)
    if (dt_min[i] < dt_min_val) dt_min_val = dt_min[i];    /* full-mesh reload of a value that
                                                              is only ever min-reduced */
/* The second pass exists only to separate the arithmetic from the reduction. The
 * cell and the criterion of the minimum, needed in the failure message, were not
 * tracked either: the C port returned cell (1,1) and "sound". Change: reduce inside
 * the first loop, drop dt_min, locate the cell afterwards and only when the step
 * is too small. */
\end{code}

\textbf{(6) Streaming stores.}
Section~\ref{sec:ceil} showed that a streaming store moves no read-for-ownership bytes on this CPU while
the C kernels' stores do, and that the Fortran build already avoids most of them. Two routes are open:
making the store streams of a loop recognisable to the core's write-streaming detector, or explicit
non-temporal stores. The pure-output loops are the candidates; the velocity update of \kernel{advec\_mom}
is not, because it loads \texttt{vel1[i]} in the same iteration and the line is in L1 when it is stored:
\begin{code}
/* advec_mom_kernel_c.c (baseline), node_flux loop, direction 1 */
#pragma omp for private(j)
for (k=y_min;k<=y_max+1;k++)
#pragma omp simd
  for (j=x_min-2;j<=x_max+2;j++)
    node_flux[i] = 0.25*(mass_flux_x[(j,k-1)] + mass_flux_x[(j,k)]
                        +mass_flux_x[(j+1,k-1)] + mass_flux_x[(j+1,k)]);
/* node_flux is written once per iteration, contiguously in j, and never loaded in
 * this loop: the pattern the write-streaming detector needs to skip the
 * read-for-ownership. The same holds for post_vol, node_mass_post, node_mass_pre
 * and mom_flux, and for the flux arrays of advec_cell. GCC has no portable
 * non-temporal store builtin for AArch64 (stnp would be inline assembly) and it
 * cannot be validated on the development machine. Change: keep every output loop
 * in this shape after (1)-(3) and let the DDR-controller counters show whether
 * the hardware drops the read. */
\end{code}
The no-write-allocate model is only an upper bound for this item; the counters decide what the hardware
grants.

\subsection{Time-only changes}
\label{sec:timeonly}
After the bytes shrink, four items move the kernels off the memory roof. \textbf{(T1)} \texttt{nowait}
between independent worksharing loops: 12.5\% of the cycles of a 128-thread run are barrier time, and
many consecutive loops of a kernel touch disjoint arrays, or the same rows under the same static schedule.
\textbf{(T2)} \texttt{-fno-math-errno}: \kernel{calc\_dt}, \kernel{ideal\_gas} and \kernel{viscosity} run
entirely scalar because GCC keeps \texttt{sqrt} as a library call that may set \texttt{errno}.
\textbf{(T3)} a vectorisable upwind loop: the advection kernels choose the upwind, donor and downwind
indices by a branch on the sign of the flux and then load through those indices; loading all candidates
and selecting the value removes the branch, and GCC additionally needs \texttt{-fno-trapping-math} to
evaluate the limiter's divisions speculatively under the select. \textbf{(T4)} tile-level parallelism
(one fork/join per tile instead of per loop) is the fallback if \texttt{nowait} is not enough. (T2) and
(T3) change only the compile command of the C kernels:
\begin{code}[language=bash]
# before: the project's GNU flags for the C kernels (Makefile, CFLAGS_GNU and OMP_GNU)
mpicc -O3 -march=native -funroll-loops -fopenmp -c kernels/*_kernel_c.c
# after: two flags added to CFLAGS_GNU (and CFLAGS_ARM); the Fortran flags are unchanged
#   -fno-math-errno     T2: sqrt() need not set errno, so GCC emits the NEON fsqrt
#                           instead of a scalar libm call (calc_dt, ideal_gas, viscosity)
#   -fno-trapping-math  T3: divisions may be evaluated speculatively, so the
#                           select-based upwind loops if-convert and vectorise
mpicc -O3 -march=native -funroll-loops -fno-math-errno -fno-trapping-math -fopenmp \
      -c kernels/*_kernel_c.c
# Neither flag changes rounding or the order of operations, and CloverLeaf enables no
# floating-point traps: the results are bit-identical and the correctness gate holds.
\end{code}

\textbf{(2) \kernel{advec\_cell} temporaries --- implemented.}
\begin{code}
/* advec_cell_kernel_c.c, update loop of the x sweep (y sweep identical with the y fluxes) */
#pragma omp for private(j)
for (k=y_min;k<=y_max;k++) {
#pragma omp simd
  for (j=x_min;j<=x_max;j++) {
    /* the four temporaries live in registers: no store, no read-for-ownership */
    double pre_mass_s  = density1[i]*pre_vol[i];
    double post_mass_s = pre_mass_s + mass_flux_x[i] - mass_flux_x[i+1];
    double post_ener_s = (energy1[i]*pre_mass_s + ener_flux[i] - ener_flux[i+1]) / post_mass_s;
    double advec_vol_s = pre_vol[i] + vol_flux_x[i] - vol_flux_x[i+1];
    density1[i] = post_mass_s / advec_vol_s;   /* same operations in the same order as  */
    energy1[i]  = post_ener_s;                 /* before: the results are bit-identical */
  }
}
/* The pre_mass, post_mass, advec_vol and post_ener arguments stay in the Fortran
 * interface but are no longer touched. */
\end{code}

/* advec_cell_kernel_c.c, sweep 1: only pre_vol is computed, the post_vol store is gone */
pre_vol[i] = volume[i] + (vol_flux_x[i+1]-vol_flux_x[i]) + (vol_flux_y[iy+1]-vol_flux_y[iy]);

\textbf{(4) Reset and Revert --- implemented.}
\begin{code}[language={[90]Fortran}]
! reset_field.f90, C path: the level-1 fields become the level-0 fields by exchanging
! the allocations; reset_field_kernel_c is no longer called
DO tile=1,tiles_per_chunk
  CALL swap_field(chunk%tiles(tile)%field%density0, chunk%tiles(tile)%field%density1)
  CALL swap_field(chunk%tiles(tile)%field%energy0,  chunk%tiles(tile)%field%energy1)
  CALL swap_field(chunk%tiles(tile)%field%xvel0,    chunk%tiles(tile)%field%xvel1)
  CALL swap_field(chunk%tiles(tile)%field%yvel0,    chunk%tiles(tile)%field%yvel1)
ENDDO

SUBROUTINE swap_field(a,b)              ! three MOVE_ALLOCs: O(1), no memory traffic
  REAL(KIND=8), ALLOCATABLE, INTENT(INOUT) :: a(:,:), b(:,:)
  REAL(KIND=8), ALLOCATABLE :: t(:,:)
  CALL MOVE_ALLOC(a,t); CALL MOVE_ALLOC(b,a); CALL MOVE_ALLOC(t,b)
END SUBROUTINE swap_field

! PdV.f90: the C corrector rewrites density1/energy1 over the whole range revert would
! copy, so the C path skips the copy; the Fortran kernels keep it
IF ( predict .AND. .NOT. use_C_kernels ) THEN
  CALL revert()
ENDIF
\end{code}

\textbf{(5) \kernel{calc\_dt} fused reduction --- implemented.}
\begin{code}
/* calc_dt_kernel_c.c: one pass; dt_min is never written (the argument stays for the
 * Fortran interface). The four limits moved to an always_inline helper so that the hot
 * loop and the diagnostic scan share one definition. */
#pragma omp for private(j,dtct,dtut,dtvt,dtdivt) reduction(min:dt_min_val)
for (k=y_min;k<=y_max;k++) {
#pragma omp simd private(dtct,dtut,dtvt,dtdivt) reduction(min:dt_min_val)
  for (j=x_min;j<=x_max;j++) {
    cell_dt_limits(j,k, ..., &dtct,&dtut,&dtvt,&dtdivt);  /* sound, x-vel, y-vel, divergence */
    dt_min_val = MIN(dt_min_val, MIN(dtct,MIN(dtut,MIN(dtvt,dtdivt))));
  }                   /* every thread and vector lane keeps a private minimum; min is
                         exact, so the order in which OpenMP combines them is irrelevant */
}
if (dt_min_val < min_dt) {        /* failure path only: serial, runs once before the abort. */
  for (k...) for (j...) {         /* Re-evaluate the limits and report the first cell that  */
    cell_dt_limits(...);          /* reaches the minimum and which of the four it was,     */
    if (MIN(dtct,MIN(dtut,MIN(dtvt,dtdivt))) == dt_min_val) {  /* instead of the fixed      */
      j_ldt=j; k_ldt=k; dtl_control=...; goto found;           /* (1,1)/"sound" of the port */
    }
  }
}
\end{code}

\textbf{(T1) \texttt{nowait} --- implemented in \kernel{advec\_mom}, open in \kernel{advec\_cell}.}
\begin{code}
/* advec_mom_prep_c, direction 1: node_mass_post -> node_mass_pre without a barrier */
#pragma omp for private(j) schedule(static) nowait  /* same k range and schedule(static) as
                                                       the next loop: OpenMP guarantees the
                                                       same row -> thread mapping, and
                                                       node_mass_pre reads node_mass_post
                                                       only in its own row */
for (k=y_min;k<=y_max+1;k++)
#pragma omp simd
  for (j=x_min-1;j<=x_max+2;j++)
    node_mass_post[IDXN(j,k)] = 0.25*(density1[IDXC(j  ,k-1)]*post_vol[IDXN(j  ,k-1)]
                                     +density1[IDXC(j  ,k  )]*post_vol[IDXN(j  ,k  )]
                                     +density1[IDXC(j-1,k-1)]*post_vol[IDXN(j-1,k-1)]
                                     +density1[IDXC(j-1,k  )]*post_vol[IDXN(j-1,k  )]);
#pragma omp for private(j) schedule(static)         /* node_flux finished at its own barrier */
for (k=y_min;k<=y_max+1;k++)
#pragma omp simd
  for (j=x_min-1;j<=x_max+2;j++)
    node_mass_pre[IDXN(j,k)] = node_mass_post[IDXN(j,k)]
                             - node_flux[IDXN(j-1,k)] + node_flux[IDXN(j,k)];
/* Also nowait: the post_vol loop (see (3)) and, in direction 1 of advec_mom_vel_c, the
 * mom_flux loop before the velocity update (same rows, same schedule). Direction 2
 * keeps its barriers because the stencils cross rows. advec_cell is still all-barrier. */
\end{code}

\textbf{(T3) Branch-free upwind loop --- implemented in \kernel{advec\_mom}, open in \kernel{advec\_cell}.}
\begin{code}
/* advec_mom_vel_c, mom_flux loop, direction 1 (direction 2 is the same along k with celldy) */
#pragma omp for private(j) schedule(static) nowait
for (k=y_min;k<=y_max+1;k++) {
#pragma omp simd
  for (j=x_min-1;j<=x_max+1;j++) {
    const double nf  = node_flux[IDXN(j,k)];
    const int    neg = (nf < 0.0);   /* flow in -j: upwind j+2, donor j+1, downwind j */
    const double v_m1 = vel1[IDXN(j-1,k)], v_0  = vel1[IDXN(j  ,k)],  /* all four candidates: */
                 v_p1 = vel1[IDXN(j+1,k)], v_p2 = vel1[IDXN(j+2,k)];  /* contiguous loads     */
    const double v_up  = neg ? v_p2 : v_m1;      /* selects replace the branch and the      */
    const double v_don = neg ? v_p1 : v_0;       /* indirect loads through upwind/donor/    */
    const double v_dwn = neg ? v_0  : v_p1;      /* downwind                                */
    const double m_don = neg ? node_mass_pre[IDXN(j+1,k)] : node_mass_pre[IDXN(j,k)];
    const double width = celldx[FTNREF1D(j,x_min-2)];
    const double w_dif = neg ? celldx[FTNREF1D(j+1,x_min-2)] : celldx[FTNREF1D(j-1,x_min-2)];
    const double sigma   = fabs(nf)/m_don;
    const double vdiffuw = v_don - v_up,  vdiffdw = v_dwn - v_don;
    const double auw = fabs(vdiffuw), adw = fabs(vdiffdw);
    const double wind = (vdiffdw <= 0.0) ? -1.0 : 1.0;
    const double lim  = wind*MIN(width*((2.0-sigma)*adw/width+(1.0+sigma)*auw/w_dif)/6.0,
                                 MIN(auw,adw));  /* always evaluated (-fno-trapping-math) */
    const double limiter = (vdiffuw*vdiffdw > 0.0) ? lim : 0.0;  /* ... then selected */
    mom_flux[IDXN(j,k)] = (v_don + (1.0-sigma)*limiter)*nf;
  }
}
/* Same arithmetic in the same order as the branchy original: bit-identical results.
 * With -fno-trapping-math GCC vectorises all 13 loops of the file (vectoriser report,
 * GCC 13, x86); the NEON share on the cluster is measured with PAPI. */
\end{code}

\section{Conclusions (draft)}
% =============================================================================
\begin{itemize}
  \item The C kernels are memory-bound (0.2\,flop/B against a 5\,flop/B ridge) and the 64$\times$2 baseline
        already sustains 94\% of the 266.5\GBs{} hardware ceiling over the whole run: only fewer bytes can
        make it faster.
  \item The analytic byte model matches the counters to 1\% and predicts the five planned changes at
        $-29\%$ of the traffic (floor 10.5 to 7.4\,s); the read-for-ownership that the C stores pay, and
        that streaming stores and the Fortran build avoid, is a sixth lever worth up to another $-23\%$.
  \item The correctness gate (reproduction of the \texttt{clover\_bm.in} deviation) held at every layout for
        the baseline and is applied to every change.
\end{itemize}
